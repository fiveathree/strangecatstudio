## 1. 需求（用戶）

- 目的：後台不能只靠一組密碼。輸入密碼後，要用自己的手機或電腦確認（指紋、臉部辨識或螢幕鎖），不用另外裝 App、不用抄數字。
- 原則：以最少、正確的程式碼守住安全底線；沿用現有帳號、session、資料庫結構，不另建登入系統，不加套件、資料表、抽象層或新管理頁。
- 使用者：店主、店員、使用主帳號的人；主要在電腦登入，也會用手機。

保留的決定：

1. 所有帳號一律必須，包括主帳號；還沒建立通行金鑰的人輸入正確密碼後只能建立，拿不到登入狀態。
2. 主帳號密碼不能直接當 API 通行證；所有後台 API 都要經過「密碼＋通行金鑰」登入取得的 session。
3. 不做「記住這部電腦」；session 12 小時。
4. 同一帳號驗證失敗 5 次，暫停登入到該 15 分鐘時段結束。
5. 備用碼：建立通行金鑰時產生 10 組一次性備用碼，只顯示一次。
6. 店主可在「帳號管理 → 修改」勾選「重設通行金鑰」；主帳號沒有裝置也沒有備用碼時，用 D1 Console 一句指令清除。

範圍外：每個帳號多於一把通行金鑰、記住裝置、驗證器 App、簡訊／Email 驗證碼、客人端登入、金流物流。

## 2. 驗收標準

全部以 `node --experimental-sqlite booking/test.mjs` 自動檢查，另加一次本機實際操作與一次線上真裝置操作。

- [ ] AC1 正常登入：未建立的帳號輸入正確密碼，只拿到建立用的一次性挑戰、沒有 session；建立通行金鑰後取得 session 與 10 組備用碼；之後以密碼＋通行金鑰可以登入。同一個已簽署的挑戰不能用第二次。
- [ ] AC2 驗證失敗：密碼正確但沒有通行金鑰，或簽名錯誤、挑戰不符、來自其他網址、通行金鑰屬於其他網站、沒有用指紋／臉部／螢幕鎖解鎖，都得到 401，拿不到 session。
- [ ] AC3 鎖定：同一帳號 15 分鐘時段內失敗 5 次後，即使通行金鑰正確也被拒絕（429）；下一個時段恢復。
- [ ] AC4 備用碼：可以代替通行金鑰登入一次，第二次用同一組被拒絕。
- [ ] AC5 舊通行方式失效：`Authorization: Bearer <ADMIN_TOKEN>` 呼叫 `/api/admin/orders` 得到 401。
- [ ] AC6 重設：店主勾選「重設通行金鑰」後，該帳號現有 session 失效，下次登入要重新建立。
- [ ] AC7 現有測試全部仍然通過。
- [ ] AC8 上線：用使用者自己的手機或電腦，以主帳號在 `fiveathree.github.io` 完成一次建立與登入。

## 3. 設計

沿用 `admin.html` 現有登入框的元素與樣式：

- 登入框：輸入密碼按「登入」後，「登入」按鈕收起，出現說明文字與一個大按鈕——第一次是「建立通行金鑰」，之後是「用通行金鑰確認」。按下後由瀏覽器／系統彈出指紋、臉部辨識或螢幕鎖。
- 「裝置不在身邊？改用備用碼」：按下後出現備用碼輸入格與「登入」按鈕（第一次建立時不顯示）。
- 取消或逾時：顯示「已取消或逾時，請再按一次」，可以再按。
- 建立後顯示 10 組備用碼與「我已存好，進入後台」。
- 帳號管理的修改表單：「重設通行金鑰」勾選格（新增帳號時不顯示）。

## 4. 實作紀錄（Claude）

### 4.0 方案

- **標準與做法**：瀏覽器內建的 WebAuthn（`navigator.credentials.create/get`）。伺服器用 Workers 內建 WebCrypto 驗證 ES256（ECDSA P-256）或 RS256 簽名，沒有自行實作密碼學。建立時用瀏覽器的 `getPublicKey()` 取得公鑰，所以不用解析 CBOR／attestation（`attestation: 'none'`）。不加套件（比較過 `@simplewebauthn/server`：要加 `package.json` 與相依，換來省約 60 行）。
- **檢查項目**：挑戰（一次性、5 分鐘有效）、`type`、來源網址（`ALLOWED_ORIGINS`）、通行金鑰的網站雜湊（rpId = 頁面的 hostname）、使用者在場＋已驗證旗標、簽名。
- **資料庫**：不用改。沿用 `staff.mfa`／`settings.master_mfa` 的 JSON：`{ passkeys: [{ id, key, alg }], backup: [雜湊], challenge, exp }`。第一版的驗證碼紀錄沒有 `passkeys`，會被當作未建立，所以上線時不用另外清資料。
- **登入 API**：仍然只有 `POST /api/admin/login`。第一次送出（只有密碼）→ 回傳挑戰；第二次送出 `passkey`（或備用碼 `code`）→ 驗證後發 session。
- **網域綁定**：通行金鑰屬於 `fiveathree.github.io`。之後搬去其他網域時，每個人要重新建立（按一次指紋）；屆時 `ALLOWED_ORIGINS` 也要改。

### 4.1 實作後填寫

- 改動檔案：`booking/worker.js`（驗證碼程式換成通行金鑰）、`booking/test.mjs`、`admin.html`、`README.md`、`CLAUDE.md`、本檔。`schema.sql` 不用改。
- 與方案不同之處：無。
- 已自測（2026-10-18，本機）：
  - `node --experimental-sqlite booking/test.mjs` → `all booking checks passed`。測試的「裝置」用 Node 內建 ECDSA（簽名為 DER 格式，與瀏覽器相同），獨立於 Worker 的 WebCrypto。
  - 反向檢查：分別拿掉簽名檢查、解鎖旗標檢查、挑戰檢查、來源網址檢查、網站雜湊檢查、鎖定，每一項測試都會失敗。
  - 本機實際操作（瀏覽器面板，沒有真的指紋裝置，在測試分頁內以 WebCrypto 暫時替換 `navigator.credentials`）：主帳號第一次登入 → 「建立通行金鑰」→ 10 組備用碼 → 進入後台；登出後再登入 →「用通行金鑰確認」→ 進入後台；「改用備用碼」以小寫輸入可登入；取消時顯示提示，再按可登入；手機寬度（375px）沒有橫向捲動。
