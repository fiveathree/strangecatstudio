# 規格：後台雙重認證（2FA）

> 一個功能一個檔。設計、實作、驗收都只看這個檔，各自填自己的章節，不改別人的章節。
>
> 狀態：開發中（本機完成，未上線）
> 建立：2026-10-17　最後更新：2026-10-18

---

## 1. 需求（用戶）

- 目的：後台目前只靠一組密碼就能看到全部客人資料、訂單與營業額，而且主帳號密碼（`ADMIN_TOKEN`）本身可以直接當 API 通行證。加上第二道驗證，並關閉這條直通路徑。
- 原則：以最少、正確的程式碼守住安全底線；沿用現有帳號、session、資料庫結構，不另建登入系統，不加套件、資料表、抽象層或新管理頁。
- 使用者：店主、店員、使用主帳號的人；主要在電腦登入，驗證碼由各人手機上的免費驗證器 App 產生（Google Authenticator、Microsoft Authenticator 等）。

已確認的 6 項決定：

1. 用驗證器 App（TOTP，6 位數、每 30 秒換一次），不用簡訊、不用 Email。
2. 所有帳號一律必須啟用，包括主帳號。還沒設定的人輸入正確密碼後只能完成設定，拿不到登入狀態。
3. 主帳號密碼不能再直接當 API 通行證；所有後台 API 都要經過「密碼＋驗證碼」登入取得的 session。
4. 不做「記住這部電腦」；每次登入（session 12 小時）都要輸入驗證碼。
5. 同一帳號驗證碼錯 5 次，暫停登入 15 分鐘。
6. 上線時清除所有現有 session，每個人下次登入都要先設定。

範圍內（只做這些）：

- 設定：顯示手動輸入用的金鑰（不顯示 QR Code，見 4.0「QR Code」），輸入一次正確驗證碼才算啟用。
- 備用碼：啟用時產生 10 組一次性備用碼，只顯示這一次；用一組少一組，不提供重新產生。
- 店主在現有「帳號管理 → 修改」勾選「重設雙重認證」，可讓店員或其他店主重新設定（例如換手機）。
- 主帳號遺失手機與備用碼：在 Cloudflare D1 Console 執行一句指令清除（見 4.0）。

範圍外（這次不做）：記住裝置、QR Code、Passkey、簡訊／Email 驗證碼、重新產生備用碼、新的復原流程、2FA 專用的操作紀錄或管理頁、客人端登入、金流物流。

## 2. 驗收標準（開工前定好，用戶確認後才開始）

每一條都能用「是／否」判斷，全部以 `node --experimental-sqlite booking/test.mjs` 自動檢查，另加一次本機實際操作。

- [ ] AC1 正常登入：未設定的帳號輸入正確密碼，只拿到設定用金鑰、沒有 session；用金鑰產生的驗證碼完成設定後取得 session 與 10 組備用碼；之後以密碼＋驗證碼可以登入。同一個驗證碼不能用來登入第二次。
- [ ] AC2 錯誤驗證碼：已設定的帳號，密碼正確但沒有驗證碼或驗證碼錯誤，得到 401，拿不到 session。
- [ ] AC3 鎖定：同一帳號驗證碼錯 5 次後，即使輸入正確驗證碼也被拒絕（429）。
- [ ] AC4 備用碼：備用碼可以代替驗證碼登入一次，第二次用同一組被拒絕。
- [ ] AC5 舊通行方式失效：`Authorization: Bearer <ADMIN_TOKEN>` 呼叫 `/api/admin/orders` 得到 401。
- [ ] AC6 重設：店主勾選「重設雙重認證」後，該帳號現有 session 失效，下次登入要重新設定。
- [ ] AC7 現有測試全部仍然通過，顯示 `all booking checks passed`。
- [ ] AC8 上線：正式 D1 已先執行 4.0 的資料庫指令才 push；上線後用使用者電腦的瀏覽器以主帳號完成一次設定與登入。

## 3. 設計

後台只多兩個小區塊，沿用 `admin.html` 現有登入框的元素與樣式，不另做視覺設計（待用戶確認是否仍要交 ChatGPT 設計）：

- 登入框：密碼下面多一格「驗證碼」，伺服器要求時才出現。
- 設定區（取代登入框）：說明「用驗證器 App 新增帳號，選『輸入設定金鑰』，類型選『時間』」，顯示金鑰（每 4 字一組）、手機上可按的「在驗證器開啟」連結、驗證碼輸入格、「完成設定」按鈕。完成後顯示 10 組備用碼與「我已抄下，進入後台」按鈕。
- 帳號管理的修改表單：多一個「重設雙重認證」勾選格。

## 4. 實作紀錄（Claude）

### 4.0 預計方案（開工前，待用戶確認）

**TOTP 做法比較**

| 方案 | 程式碼 | 缺點 |
|---|---|---|
| A. 用 Workers 內建 WebCrypto 的 HMAC-SHA-1，加 RFC 6238 的截取與 Base32 解碼 | 約 15 行，無套件 | 要自己寫截取那幾行（不是密碼學演算法本身） |
| B. npm 套件（例如 `otpauth`） | 呼叫約 5 行 | Worker 目前零相依；要加 `package.json`、依賴版本與供應鏈風險，換來省 10 行 |

選 A。HMAC 由平台的標準函式庫計算，沒有自行實作密碼學。已用 Node 24 對 RFC 6238 附錄 B 的官方測試數據驗證原型，4 組全部相符；測試檔另用 Node 內建的 `crypto.createHmac` 獨立產生驗證碼，兩邊互相對照。

**QR Code**：要在瀏覽器畫 QR Code 必須加一個第三方程式庫到後台頁面，或自己寫編碼器。這次不做，改為顯示金鑰與 `otpauth://` 連結（手機上按下可直接加入部分驗證器 App）。代價是在電腦設定時要手動輸入 32 個字元，一次性。

**資料庫（只改一處）**

- `staff` 加一個欄位 `mfa TEXT`：存 JSON `{ secret, step, backup }`（金鑰、最後一次用過的時間格、備用碼的 SHA-256 雜湊）。`NULL` = 未設定。
- 主帳號沒有 `staff` 資料列，用現有 `settings` 表的一列 `master_mfa`，格式相同。
- 不新增資料表、不改 `sessions`：未完成 2FA 時根本不發 session，所以不需要「半登入」狀態。
- 鎖定沿用現有 `rate_limits` 表（每個帳號一個 key，15 分鐘一格）；原本每個 IP 的登入次數限制不變。
- 防重播與備用碼一次性：更新時用 `UPDATE … WHERE mfa = 舊值`，一句 SQL 內比對，同時送出的兩個請求只有一個成功。

**上線前要在正式 D1 執行（push 之前）**

```sql
ALTER TABLE staff ADD COLUMN mfa TEXT;
DELETE FROM sessions;
```

**主帳號遺失手機及備用碼時（D1 Console 一句）**

```sql
DELETE FROM settings WHERE key = 'master_mfa';
```

店員或店主遺失：由其他店主在後台勾選「重設雙重認證」；沒有其他店主時，在 D1 Console 執行 `UPDATE staff SET mfa = NULL WHERE username = '帳號';`。

**登入流程（只改 `POST /api/admin/login`，不加新 API）**

1. 密碼錯 → 401（不變）。
2. 該帳號 15 分鐘內驗證碼已錯 5 次 → 429。
3. 未設定：沒附金鑰與驗證碼 → 回傳新金鑰（不發 session）；附上金鑰與正確驗證碼 → 存入、產生 10 組備用碼、發 session。
4. 已設定：驗證碼（或備用碼）正確 → 發 session；錯誤或沒填 → 401，並計一次錯誤。

**預計修改檔案**

| 檔案 | 改動 |
|---|---|
| `booking/worker.js` | `identify()` 刪除 `ADMIN_TOKEN` 直通那一行；`login()` 加上述流程；新增 TOTP 驗證約 15 行；`PUT /api/admin/staff/:id` 接受 `resetMfa`；備份匯出的 `settings` 排除 `master_mfa`；操作紀錄遮蔽 `code`、`secret` 欄位 |
| `booking/schema.sql` | `staff` 加 `mfa` 欄位 |
| `booking/test.mjs` | 加一個登入小工具（自動完成設定），把 80 處直接用 `test-token` 的地方改為用登入取得的 session；加入 AC1–AC6 的檢查 |
| `admin.html` | 登入框加驗證碼格、設定區、備用碼顯示；帳號修改表單加勾選格 |
| `README.md` | 「後台帳號與安全」一節改寫登入方式與 D1 重設指令 |
| `CLAUDE.md` | 第 3、5 節註明主帳號密碼不再是通行證、`mfa` 欄位不可匯出 |

不改：`notify.gs`（不用更新 GAS）、公開網站頁面、字型、`sessions`、`audit` 結構。

### 4.1 實作後填寫

- 改動檔案：`booking/worker.js`、`booking/schema.sql`、`booking/test.mjs`、`admin.html`、`README.md`、`CLAUDE.md`。
- 與方案不同之處及原因：
  - 操作紀錄沒有另外遮蔽 `code`、`secret`：登入不經過操作紀錄的流程，這兩個欄位根本不會被記下，不用改。
  - 加了一處：用備用碼登入時，操作紀錄的「登入」一筆內容寫「使用備用碼」（一行，沿用現有紀錄）。
  - `test.mjs` 原有一條報表檢查會因日期失敗（預約排到下個月時，「最新月份」不是本月）。改為對照本月；與 2FA 無關，原本的程式在今天（2026-10-18）也一樣失敗。
- 已自測（2026-10-18，本機）：
  - `node --experimental-sqlite booking/test.mjs` → `all booking checks passed`。AC1–AC6 都有對應檢查；測試的驗證碼由 Node 內建 HMAC 獨立產生，並先對照 RFC 6238 官方數據。
  - 本機實際操作（本機測試 API＋靜態伺服器，瀏覽器面板）：主帳號第一次登入 → 出現金鑰 → 錯誤驗證碼顯示錯誤、金鑰不變 → 正確驗證碼 → 顯示 10 組備用碼 → 進入後台；另開分頁再登入只要求驗證碼；用小寫輸入備用碼可登入；新增店員帳號時沒有「重設雙重認證」，修改時才有；店員以手機寬度（375px）完成設定，沒有橫向捲動。
  - 本機操作時發現並修正：按「我已存好，進入後台」後備用碼框沒有收起。
- 未能驗證：正式 D1 與線上 Worker（未上線）；真手機上的驗證器 App 與 `otpauth://` 連結；Cloudflare D1 Console 的重設指令（只在本機 SQLite 驗證過語法）。
